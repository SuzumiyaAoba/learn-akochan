# 状態・麻雀ルール・点数計算

この文書は、Akochan の共有ライブラリ（`akochan/share`）が、MJAI のイベント列をどのような局面に変換し、手牌の待ち・役・符をどのように判定し、点数をどのように点棒移動へ変換するかを説明する。既存の全体像は [`akochan-architecture.md`](./akochan-architecture.md) にあり、本書はそのうち「状態」「ルール判定」「点数」の実装仕様を、ソースを読まずに追える形に掘り下げる。

ここでいう「実装仕様」は、一般的なリーチ麻雀のルールと異なる場合も含めた現在のコードの動作である。特に、状態復元はイベントを検証する処理ではなく、イベントをそのまま再生する処理である。入力棋譜の妥当性は別途確認する必要がある。

## 1. 全体の流れ

共有層の処理は、概ね次のパイプラインで進む。

```text
Moves（時系列 JSON）
  ↓ 最新の start_kyoku からイベントを再生
Game_State（4人の手牌・副露・河・立直状態・点数）
  ↓ 牌を種類へ正規化
Tenpai_Info（通常形/七対子のシャンテン値と待ちごとの Agari_Info）
  ↓ 和了形ごとに役・符を計算
Agari_Info（ツモ時/ロン時の翻と符）
  ↓ 支払者、親、積み棒、本場を適用
4人分の点数移動（ten_move_hora / ten_move_ryukyoku）
```

合法手の生成はこの逆方向ではなく、最後のイベントの種類から候補を列挙し、現在の `Game_State` と上の和了判定を使って候補を絞り込む。

## 2. 牌の表現

### 2.1 牌番号と文字列

手牌は 38 要素の `Hai_Array`（添字 0〜37）で、各添字は「その牌を何枚持つか」を表す。添字 0 は使わない。

| 牌 | 通常の添字 | 赤牌の添字 | JSON 文字列 |
|---|---:|---:|---|
| 萬子 1〜9 | 1〜9 | 10（赤5萬） | `1m`〜`9m`, `5mr` |
| 筒子 1〜9 | 11〜19 | 20（赤5筒） | `1p`〜`9p`, `5pr` |
| 索子 1〜9 | 21〜29 | 30（赤5索） | `1s`〜`9s`, `5sr` |
| 東・南・西・北 | 31〜34 | — | `E`, `S`, `W`, `N` |
| 白・發・中 | 35〜37 | — | `P`, `F`, `C` |

`hai_str_to_int` と `hai_int_to_str` はこの対応を相互変換する。未知文字列は入力エラーとして assert され、特別な `?` だけは `-1` に変換される。`is_valid_hai` が受け入れるのは 1〜37 なので、`?` は状態へ追加されない。

`get_hai38` は 136 枚形式の物理牌 ID を上の 38 種類へ変換する。通常は `色 = hai136 / 36`、`数字 = (hai136 % 36) / 4 + 1` で求め、物理 ID 16、52、88だけは赤5の 10、20、30 として扱う。

### 2.2 牌種への正規化と赤5

`haikind(hai)` は赤5を通常の5へ戻す。

```text
haikind(10) = 5       haikind(20) = 15       haikind(30) = 25
その他は同じ添字
```

したがって、例えば `[5] = 3, [10] = 1` は牌種として `[5] = 4` になる。シャンテン・待ち・役判定は原則この正規化後に行い、赤ドラの有無を残したい点数処理では元の配列も使う。`haikind(Hai_Array)` は赤の枚数を通常牌の枚数へ合算するため、正規化後は「どの1枚が赤だったか」は分からない。

副露は `Fuuro_Elem` で表す。

| `type` | 内容 | `hai` | `consumed` |
|---|---|---|---|
| `FT_CHI` | チー | 鳴いた捨て牌 | 手牌から出した2枚 |
| `FT_PON` | ポン | 鳴いた捨て牌 | 手牌から出した2枚 |
| `FT_DAIMINKAN` | 大明槓 | 鳴いた捨て牌 | 手牌から出した3枚 |
| `FT_ANKAN` | 暗槓 | 通常は未設定 | 手牌から出した4枚 |
| `FT_KAKAN` | 加槓 | 追加した1枚 | 既存ポンを構成する3枚 |

`target_relative = (4 + target - actor) % 4` は、鳴いた人から見た捨て主の相対位置である。1 は下家、2 は対面、3 は上家を表す。門前判定は「暗槓以外の副露がないこと」なので、暗槓だけなら門前として扱う。

### 2.3 ドラ

ドラ表示牌からドラ牌への対応は、数牌では 1→9、9→1、それ以外は次の数字へ進む。字牌は風が 東→南→西→北→東、三元牌が 白→發→中→白 の循環である。`count_dora` は、手牌・副露のドラ牌種数と、手牌/副露中の赤5枚数を合算する。副露の赤5も数えるが、暗槓の `hai` フィールドは無視し、`consumed` を見る。

## 3. イベント列から局面を復元する

### 3.1 局面の中身

`Game_State` は次を持つ。

| 項目 | 意味 |
|---|---|
| `bakaze` | 場風。東・南・西・北を 0〜3 で保持 |
| `kyoku` | 局番号 1〜4 |
| `honba` | 本場数 |
| `kyotaku` | 供託本数 |
| `dora_marker` | 表ドラ表示牌の配列 |
| `player_state[4]` | 4人分の `Player_State` |

各 `Player_State` は点数、自風、`tehai`、副露、河、`reach_declared`（立直宣言済み）、`reach_accepted`（立直成立済み）を持つ。自風は親を 0 とし、座順に `(4 + pid - oya) % 4` で決める。

### 3.2 再生アルゴリズム

`get_game_state` は棋譜を先頭から無条件に読むのではなく、末尾から直近の `start_kyoku` を探し、そのイベントから最後までを再生する。再生時の入力→状態変化は次の通り。

| イベント | 状態への反映 |
|---|---|
| `start_kyoku` | 4人の手牌・副露・河・立直フラグを初期化し、場風、局、本場、供託、点数、親、自風、初期ドラを設定 |
| `dora` | 表ドラ表示牌を末尾に追加 |
| `tsumo` | `pai` が有効なら、その牌を `actor` の手牌へ1枚追加 |
| `dahai` | `actor` の河に牌・ツモ切り・立直宣言中フラグを追加し、同じ牌を手牌から1枚減らす |
| `reach` | `reach_declared = true` |
| `reach_accepted` | `reach_accepted = true`、点数を1000減らし、供託を1本増やす |
| `chi` / `pon` / `daiminkan` | `consumed` を手牌から減らし、鳴いた牌と相対位置を副露へ追加 |
| `ankan` | `consumed` 4枚を手牌から減らし、暗槓を副露へ追加 |
| `kakan` | 追加牌を手牌から減らし、同じ牌種のポンを加槓へ置換 |
| `hora` | 供託を0にするだけ |
| `start_game`, `end_kyoku`, `none`, `ryukyoku`, `end_game` | 局面のフィールドを変更しない |

`start_kyoku` は配牌 4人×13枚、`scores`、`oya`、`bakaze`、`kyoku`、`honba`、`kyotaku`、`dora_marker` を想定する。`haiyama` がイベントにあっても状態復元では使わない。配牌の `?` のような無効牌は追加されず、`go_next_state` 自体はイベントの枚数・順序を検証しない。

例えば、配牌の `5m` が2枚、`tsumo` で `5mr`、続いて `dahai` で `5mr` を捨てた場合、再生中の配列では一時的に赤5の添字10が増え、最後はその添字が減る。通常の `5m` と赤5を同一牌種として照合する処理は、必要な箇所で `haikind` を呼ぶ。

### 3.3 状態復元上の注意

`hora` の点数配列は `Game_State` に反映されない。状態に入る点数は `start_kyoku` の点数から立直供託分だけを引いた値であり、和了点の移動は `agari_ten` の戻り値や次局の `start_kyoku` で確認する。したがって、和了直後の同一イベント列を「得点後の局面」として利用する場合は別途扱う必要がある。

立直・一発・フリテン用の補助判定はイベントを後ろ向きに走査する。

- 立直成立は、直近の `start_kyoku` までの間に自分の `reach_accepted` があるかで判定する。
- 一発有効性は、自分の捨て牌、または自分の捨て牌を対象にしたチー・ポン・大明槓が現れると無効にする。暗槓・加槓はこの判定では無効化要因に含まれない。
- ツモ回数は、通常ツモと嶺上ツモを分けて数える。大明槓・加槓の直後、または暗槓→ドラ→ツモの並びを嶺上ツモとし、合計70回以下を想定する。
- フリテン配列は牌種単位で作る。自分の過去の捨て牌を記録し、立直前後や直近捨て牌の扱いを後ろ向き走査の位置で決める。ロン判定では、現在の待ちのうち1種類でもフリテンなら和了を拒否する。

## 4. シャンテンと待ち

### 4.1 入力から待ち情報を作る

`cal_tenpai_info(bakaze, jikaze, tehai, fuuro)` の入力は、通常は「ツモ牌をまだ含めない13枚の手牌」と副露である。処理は次の通り。

1. 手牌と副露を牌種へ正規化する。
2. 手牌から雀頭候補を1つ選ぶ場合と、雀頭を選ばない場合を作る。
3. 残りから刻子を可能な限り選び、各結果から順子を可能な限り選ぶ。
4. 残った牌が待ちを作れる形か調べる。
5. 待ち牌が自分の手牌と副露で4枚すべて使用済みなら、その待ちは捨てる。
6. 各待ちについて役・符を計算し、`Agari_Info` を `agari_vec` に追加する。

### 4.2 通常形の待ち

残った牌の枚数による待ち判定は以下である。順子の候補は数牌だけで、字牌からは作らない。

| 残り | 待ち種別 | 条件 |
|---:|---|---|
| 1枚 | 単騎 (`MT_TANKI`) | 残り1枚と同じ牌を引く |
| 2枚 | シャンポン (`MT_SHABO`) | 同じ牌2枚。どちらかを刻子にする |
| 2枚 | 両面 (`MT_RYANMEN`) | `ab` の外側2種。`23` なら1/4、`78` なら6/9 |
| 2枚 | 嵌張 (`MT_KANCHAN`) | `a,c` の間の1種。例 `13`→2 |
| 2枚 | 辺張 (`MT_PENCHAN`) | `12`→3 または `89`→7 |

例えば `123m 456m 789m 11p 45s` は、3つの完成順子、雀頭 `11p`、未完成の `45s` からなり、`3s` と `6s` の両面待ちになる。`3s` を加えると `345s`、`6s` を加えると `456s` となる。

同じ待ちが複数の分解で成立する場合、`agari_vec` は重複排除せず、分解ごとの `Agari_Info` を複数持ち得る。和了形に含まれる役の選択も分解に依存するため、呼び出し側はベクトル全体を扱う必要がある。

### 4.3 七対子と「シャンテン値」の意味

七対子の計算は、牌種ごとに2枚以上ある種類を `head_num`、1枚だけの種類を `koritu_num` として次で求める。

```text
七対子値 = 13 - 2 × head_num - min(7 - head_num, koritu_num)
```

七対子の待ちなら、対子6種類と単独牌1種類の形から単騎待ちを `agari_vec` に追加する。副露が1つでもある場合は七対子計算を行わず、初期値6のまま扱う。

注意点として、共有層の通常形の `mentu_shanten_num` は一般的な1シャンテン、2シャンテンを数える実装ではない。初期値は8で、通常形の即時待ちを見つけた時だけ0になる。七対子側だけは上の式で0〜6（完全形では-1になり得る）を設定する。したがって、この関数の `shanten_num()` は「通常形の正確なシャンテン数」としてではなく、主に聴牌判定・七対子比較・待ち列挙の結果として読む。

`using_array` に含まれるのは自分の手牌と副露だけであり、河や他家の見えている牌は含まれない。この共有関数単体では、他家の捨て牌を見て残り枚数を減らす処理はしない。

## 5. 役・翻の計算

### 5.1 `Agari_Info` の出力

各候補は次の4値を持つ。

| 値 | 意味 |
|---|---|
| `hai` | 待ち牌（正規化後の牌種） |
| `han_tsumo` / `fu_tsumo` | ツモ和了として使う翻・符 |
| `han_ron` / `fu_ron` | ロン和了として使う翻・符 |

`calc_agari` は待ち牌、待ち種別、手牌分解、副露、場風、自風を入力にして、まず門前・色・断么九・混老頭などを判定し、通常形/七対子の構造役を足す。ドラ、裏ドラ、立直、一発、海底、河底はこの関数の役加算には含まれない。

### 5.2 実装されている通常役

下表の「閉門/副露」は、門前かどうかによる翻数の違いで、ツモ/ロン共通の値である。門前ツモだけは `han_tsumo` に追加される。

| 役 | 実装上の条件 | 翻 |
|---|---|---:|
| 役牌 | 場風、自風、三元牌の刻子/槓子。各牌ごとに加算 | 1/牌 |
| 門前清自摸和 | 門前（暗槓だけは門前） | ツモのみ +1 |
| 平和 | 副露なし、両面待ち、刻子なし、価値牌でない雀頭 | 1 |
| 七対子 | 7種類の対子 | 2 |
| 断么九 | 手牌・副露・待ちがすべて2〜8の数牌 | 1 |
| 対々和 | チーなし、すべて刻子/槓子、単騎またはシャンポン | 2 |
| 一盃口 / 二盃口 | 門前で同一順子が2組 / 2組の重複が2つ | 1 / 3 |
| 小三元 | 三元牌2組が刻子、残りが雀頭 | 2 |
| 混老頭 | 么九牌・字牌だけで、順子なし | 2 |
| 三槓子 | 槓子が3つ | 2 |
| 三色同刻 | 同じ数字の刻子を3色 | 2 |
| 清一色 | 1色の数牌だけ | 門前6 / 副露5 |
| 混一色 | 1色の数牌と字牌だけ | 門前3 / 副露2 |
| 純全帯么九 | 全面子・雀頭に么九牌を含み、字牌なし | 門前3 / 副露2 |
| 混全帯么九 | 全面子・雀頭に么九牌または字牌を含む | 門前2 / 副露1 |
| 三色同順 | 3色に同じ順子 | 門前2 / 副露1 |
| 一気通貫 | 同一色の123・456・789 | 門前2 / 副露1 |
| 三暗刻 | 暗刻が3つ | 2 |

役の重複はコード上の排他的な置換もある。清一色なら混一色を数えず、純全帯么九なら混全帯么九を数えず、混老頭と清老頭が同時に成立する場合は混老頭を消す。七対子では役牌、平和、対々和などの通常形構造役を無効にする一方、清一色・混一色・断么九・混老頭・字一色のような全体の牌種から判定できる役は残る。

### 5.3 役満と待ちによる例外

次のいずれかが成立すると、`han_tsumo` と `han_ron` をともに13にする。

- 清老頭（純全帯么九かつ対々和）
- 大三元
- 四槓子
- 九蓮宝燈
- 字一色
- 大四喜 / 小四喜
- 四暗刻（暗刻4つ）

3つの暗刻がありシャンポン待ちの場合は、和了牌をツモすると4つ目の暗刻が成立するため、ツモ側を四暗刻として13翻にする。ロンではその牌で完成する刻子が明刻扱いになるため、ロン側は三暗刻の翻を残す。これは四暗刻単騎ではない。4つの暗刻を通常に数えられる場合は両方13翻になる。

暗刻数は「正規化後の手牌にちょうど3枚ある刻子」と暗槓を数える。役判定は手牌分解と待ち種別に依存するので、同じ牌姿でも待ちの選び方で三暗刻/四暗刻の扱いが変わる。

### 5.4 役判定の実装上の制約

- 役牌は副露の `consumed[0]`、または手牌の刻子/シャンポン待ちを調べる。副露データの3枚が同じ牌種であることは、前段の合法性に依存する。
- 平和は副露が空であること、両面待ち、刻子なし、場風・自風・三元牌の雀頭でないことだけを見ている。待ち牌の種類が価値牌であるかではなく雀頭と待ち種別で判断する。
- 役牌の場風と自風が同じ場合、両方のフラグを加算するため、親の連風牌は2翻になる。
- 清一色・混一色・字一色の色検査は、共有呼び出し経路では `tehai` と副露を中心に行い、待ち牌を検査しない関数がある。通常の `cal_tenpai_info` から使う場合、待ち牌を含めた最終14枚の色が必要なケースでは、呼び出し側で結果を確認する必要がある。

`make_hora` は計算を行う関数ではない。拡張版は呼び出し側から渡された翻・符・点数を JSON の `fan`、`fu`、`scores` として記録し、裏ドラ表示牌があれば `uradora_marker` を追加する。

## 6. 符の計算

### 6.1 早期に確定する形

役判定で平和または七対子が成立した場合、他の符を積まず、直ちに次を返す。

```text
平和       : ツモ20符、ロン30符
七対子     : ツモ25符、ロン25符
```

それ以外は、次の順で `fu_tsumo` と `fu_ron` を作る。

### 6.2 符の部品

| 部品 | 中張牌 | 么九牌・字牌 |
|---|---:|---:|
| 明刻（ポン） | +2 | +4 |
| 明槓（大明槓・加槓） | +8 | +16 |
| 暗刻 | +4 | +8 |
| 暗槓 | +16 | +32 |

計算の初期値はツモ20符である。手牌中の刻子、手牌中の価値ある雀頭（場風・自風・三元牌）はそれぞれ+2符、単騎・嵌張・辺張待ちは+2符となる。シャンポン待ちで和了牌が刻子を完成させる場合は、中張牌ならツモ+4/ロン+2、么九牌・字牌ならツモ+8/ロン+4を加える。

その後、ツモには一律+2符、門前ロンには+10符を加え、ツモ/ロンそれぞれ30符未満なら30符にする。従って通常の非平和形では、ツモは最低30符、門前ロンでも最低30符になる。`ceil_fu` という補助関数は10符単位へ切り上げるが、`calc_fu` 自身はその関数を呼ばない。明刻・待ち・ツモ符などを単純加算するため、通常の10符単位に丸める前の値（例: 32符、38符）をそのまま返し得る。

点数表側も注意が必要である。`agari_ten` の1〜4翻は、25符の特例と `fu <= 30`、`fu <= 40`…の境界で分岐する表であり、`calc_fu` の結果を自動的に `ceil_fu` へ渡してはいない。32符や38符は境界上では次の区分へ入るが、110符を超えるなど表の範囲外の値は未対応となり assert し得る。標準的な10符単位の符として扱う契約が必要な呼び出し側は、点数表へ渡す前に `ceil_fu` を適用する必要がある。

例として、門前の平和手は早期分岐でツモ20符・ロン30符になる。一方、平和でない門前ロンは、同じ構成のツモ符に門前ロン10符を加えた値になる。七対子は刻子や待ち符を一切足さず、常に25符である。

## 7. 点数と点棒移動

### 7.1 和了点

`ron_agari` と `tsumo_agari_loss` は、翻・符・親子を入力にしてハードコードされた点数表を返す。基本的な読み方は次の通りである。

| 翻 | 非親ロン | 親ロン | 非親ツモ（親/子1人） | 親ツモ（1人） |
|---:|---:|---:|---:|---:|
| 5（満貫） | 8,000 | 12,000 | 4,000 / 2,000 | 4,000 |
| 6〜7（跳満） | 12,000 | 18,000 | 6,000 / 3,000 | 6,000 |
| 8〜10（倍満） | 16,000 | 24,000 | 8,000 / 4,000 | 8,000 |
| 11〜12（三倍満） | 24,000 | 36,000 | 12,000 / 6,000 | 12,000 |
| 13以上（役満） | 32,000 | 48,000 | 16,000 / 8,000 | 16,000 |

1〜4翻は符ごとの表で、一般的には `fu × 2^(han+2)` を基礎点として100点単位に切り上げ、ロンは非親4倍/親6倍、ツモは非親が親2倍・子1倍、親が全員2倍と考えればよい。コードはこの結果を直接分岐表で返すため、通常あり得ない組み合わせ（例: 1翻25符）も呼び出すと、その分岐表の値が優先される。翻0は0点、表の範囲外はエラーになる。

`tsumo_agari` は、親の和了なら1人分の支払いを3倍、子の和了なら親1人分と子2人分を足して総和を返す。例えば子の2翻30符ツモは親1,000点、子各500点、総額2,000点である。子の2翻30符ロンは2,000点、親の2翻30符ロンは2,900点になる。

### 7.2 本場・供託を含む点数移動

`ten_move_hora(who, from_who, han, fu, oya, ba, bou, double_ron_after_flag)` の出力は、各プレイヤーの点数差 `[pid0, pid1, pid2, pid3]` である。

- 和了者には和了点を加える。
- 本場 `ba` は、ロンなら和了者+`ba×300`、放銃者-`ba×300`。ツモなら和了者+`ba×300`、各支払者-`ba×100`。
- 供託 `bou` は和了者に `bou×1000` を加える。誰かの点数から直接引く処理ではなく、供託プールからの移動として表現される。
- ダブルロン以降を示す `double_ron_after_flag` が真なら、供託分だけ `bou=0` にして、同じ供託を二重に渡さない。
- ツモの支払額は親子で変わるが、ロンは放銃者だけが和了点を支払う。

### 7.3 流局のノーテン罰符

`ten_move_ryukyoku` は4人のテンパイ真偽だけを入力し、テンパイ人数に応じて次を返す。0人または4人テンパイなら全員0点である。

| テンパイ人数 | テンパイ者 | ノーテン者 |
|---:|---:|---:|
| 1人 | +3,000 | 各-1,000 |
| 2人 | 各+1,500 | 各-1,500 |
| 3人 | 各+1,000 | -3,000 |

本場・供託はこの関数では扱わない。

## 8. 合法手の判定と候補生成

### 8.1 2段階の検査

合法性は、JSON の形だけを見る検査と、現在局面を見る検査に分かれる。

1. `is_valid_*` はイベント種別、`consumed` の枚数、牌種関係、座順関係を調べる。
2. `is_legal_*` は直前イベント、現在の手牌、副露、立直状態、ツモ回数、待ち・フリテンを調べる。

従って、`is_valid_pon` が真でも、手牌に同じ牌が2枚なければ合法ではない。

### 8.2 単発イベント

| 行動 | 入力から見た合法条件 |
|---|---|
| 打牌 `dahai` | 直前が自分の `tsumo`。ツモ切りなら `pai` は直前のツモ牌と完全一致。手出しならツモ牌を一旦手牌から除いた後、指定牌が1枚以上残る。立直成立後はツモ切りだけ |
| チー | 直前が `dahai`、対象は上家（`actor=(target+1)%4`）、順子になる2枚を手牌に持つ、未立直、ツモ総数が70でない |
| ポン | 直前が `dahai`、対象が他家、同一牌種2枚を持つ、未立直、ツモ総数が70でない |
| 大明槓 | ポンと同じ直前条件で、同一牌種3枚を持つ |
| 暗槓 | 直前が自分の `tsumo`、同一牌種4枚の `consumed` が手牌にある。立直後の暗槓条件は未実装の TODO が残る |
| 加槓 | 直前が自分の `tsumo`、既存ポンの3枚と指定 `consumed` が同じ実牌組合せで、追加牌を手牌に持つ。成立済み立直の禁止検査はない |
| ツモ和了 | 直前が自分の `tsumo` で、和了牌が直前牌と一致し、待ち情報に同じ牌があり、ツモ翻+立直/海底補正が1以上 |
| ロン | 直前が他家の `dahai` または `kakan` で、和了牌が直前の牌と一致し、待ち情報に役がある。待ちのどれか1種類でもフリテンなら拒否 |
| 九種九牌 | 直前が自分の最初の `tsumo` 相当で、自分の河が空、全員副露なし、么九牌・字牌の種類数が9以上 |
| `none` | 直前が自分のツモ・立直・チー・ポンでなければ通る。パスの対象・優先順位を完全には検証しない |

和了の「役がある」は、`cal_tenpai_info` が返す `han_tsumo`/`han_ron` に、立直成立なら+1、ツモ回数が70なら+1、加槓へのロンなら+1を加えた値で判定する。ここでもドラや一発は加算されない。ロンは待ち情報の全要素を対象にフリテンを検査するため、現在当たった1牌が自分の捨て牌でなくても別の待ち牌がフリテンなら拒否される。

### 8.3 複合イベント（鳴き/立直＋打牌）

チー、ポン、立直は、通常その直後に打牌を伴うため、2イベントの組として検査する。

- 立直＋打牌: 未立直、門前、点数1,000以上、ツモ総数66以下、打牌後に待ちが1つ以上あること。立直は「役がある」ではなく「聴牌している」だけで成立し、立直自体が和了時の役になる。
- ポン/チー＋打牌: 鳴きが合法で、消費牌と直後の打牌を手牌から引いても枚数が負にならないこと。
- チーの食い替え: 鳴いた牌を捨てることを禁止し、鳴いた牌が順子の端だった場合に、その順子の外側へ出る牌（例: 3を鳴いた123で6を捨てる、または7を鳴いた789で4を捨てる）を禁止する。

### 8.4 生成される候補の順番

`get_all_legal_moves` は、最後のイベントに応じて次の種類を順に集約する。

```text
ツモ切り → 手出し → ポン＋打牌 → チー＋打牌
→ 大明槓 → 暗槓 → 加槓 → 立直＋打牌
→ ツモ和了 → ロン
```

直前が `dahai` なら、候補があるプレイヤーごとに `none` も追加する。チーは対象の次のプレイヤーだけ、ポン/大明槓/ロンは他の3人を走査する。九種九牌は個別の合法性関数では判定できるが、この候補集約には含まれない。

赤5を含む鳴きは、通常5の捨て牌に対して通常牌版と赤牌消費版を列挙する。ただし列挙側の条件は添字の末尾が5であるかを見ているため、赤5そのもの（10/20/30）が直前の捨て牌である場合に赤版候補が追加されないことがある。

## 9. 重要な実装上の例外・境界

利用者が「標準ルールどおり」と仮定すると誤解しやすい点をまとめる。

1. **通常形の正確なシャンテン数は共有層から得られない。** `mentu_shanten_num` は初期8、即時待ち発見時0であり、1〜7を段階的に返すものではない。AI側の別の解析器と混同しない。
2. **見えている牌の残り枚数を待ち計算に入れない。** `using_array` は自分の手牌と副露だけで、河・他家手牌・ドラ表示牌は入らない。
3. **状態復元はイベント検証をしない。** 不正な `dahai` は手牌を負にし得る。`is_valid_game_record` も最初が `start_game`、2番目が `start_kyoku` であることしか見ない。
4. **牌文字列を `int_value()` で比較する箇所がある。** チー、ポン、大明槓の合法性で、JSON の文字列 `pai` を `int_value()` として直前捨て牌と比較している。json11 の文字列の `int_value()` は0なので、意図した文字列一致検査にならない。牌種・手牌枚数による別の検査は残るが、対象牌の一致だけに依存しない入力検証が必要である。
5. **槓の海底境界が一貫しない。** ツモ総数70のとき、チー/ポン/大明槓は拒否されるが、暗槓/加槓は `>70` の検査なので70で通り得る。和了側はツモ/ロンを問わず総数70を海底相当の+1翻として扱う。
6. **立直成立後の一部制約が未実装である。** 暗槓の立直後条件には TODO があり、加槓には成立済み立直の禁止検査がない。立直宣言後の打牌はツモ切りだけである。
7. **一発判定は暗槓・加槓を無効化要因にしない。** 自分の捨て牌と、その捨て牌を鳴かれた場合だけを後ろ向きに見ている。
8. **和了後の点数は `Game_State` に反映されない。** `hora` は供託を0にするだけで、点数は次の局の開始イベントか、点数移動関数の戻り値で扱う。
9. **和了情報は役満を含めて「翻」として表す。** 役満は13翻として点数表へ渡す。役満の重複数や数え役満の別表現はない。
10. **ロンの対象フィールドは汎用検査では弱い。** `is_legal_hora` は直前イベントの actor と action の target の一致を独立には検査せず、候補生成側が作る `target` に依存する。ツモ和了でも target の値自体は主要条件になっていない。
