# Akochan の実行環境・対局進行・MJAI 連携

本書は、Akochan を起動して自己対局・ログ解析・MJAI 連携を行うときの実行モデルを説明します。対局の状態、イベント、二段階行動、外部プロトコルを先に説明し、OS や実装ファイルに依存する事項は「実装対応」と「実装上の境界」に分けます。

AI が候補を作る仕組みと確率評価は [01-overview.md](01-overview.md)、[03-ai-search-and-decision.md](03-ai-search-and-decision.md)、[04-models-evaluation-and-parameters.md](04-models-evaluation-and-parameters.md) を参照してください。

## この章のゴール

読み終えたら、次のことを説明できるようになることを目指します。

- 自己対局、ログ確認、標準入出力、一手 API、MJAI TCP の使い分け
- イベント列を受け取り、判断点で 1 または 2 イベントを返す流れ
- 設定・固定パラメータ・実行基準ディレクトリが起動に与える影響

前提は [全体像](01-overview.md) とイベント列の考え方です。局面・合法性の前提を確認したい場合は、先に [02-state-rules-scoring.md](02-state-rules-scoring.md) の 1〜3 節を読んでください。ビルド操作そのものは、変更していない [akochan/readme_jpn.md](../akochan/readme_jpn.md) を参照します。

AI がどの候補を選ぶかを知りたい場合は [03-ai-search-and-decision.md](03-ai-search-and-decision.md)、確率と順位評価を知りたい場合は [04-models-evaluation-and-parameters.md](04-models-evaluation-and-parameters.md) へ戻ってください。

## 1. 実行モデル

Akochan は、現在の盤面を一度だけ受け取るのではなく、MJAI のイベント列を順に蓄積します。局開始からのイベントを再生すると現在局面が得られ、判断が必要なイベントが末尾に来たときだけ AI が候補を比較します。

| 論理的な役割 | 内容 |
|---|---|
| イベント記録 | 局開始、ツモ、打牌、鳴き、和了、流局などを時系列で保持 |
| 局面復元 | 最新の局開始から手牌、副露、河、立直、点数を再生 |
| 判断 | 自分のツモ、または他家の打牌・加槓に対して候補を比較 |
| 対局進行 | 山、配牌、ツモ、鳴き、和了、流局、次局をイベントとして追加 |
| 入力アダプタ | CLI、ファイル、標準入出力、TCP の差をイベント列へ吸収 |
| 出力アダプタ | 最良候補を1件または2件の MJAI イベントとして返す |

入力経路が違っても、イベント列の形式と判断の流れは共通です。設定と固定パラメータは通常、起動した作業ディレクトリからの相対位置で読み込まれるため、リポジトリの運用資料どおりのディレクトリから実行します。

## 2. 判断コアと実行アダプタ

### 2.1 生成と配置の関係

Akochan の実行環境は、候補生成・確率評価・行動選択を担う判断コアと、自己対局・ログ解析・標準入出力・TCP をイベント列へ接続する実行アダプタに分かれます。生成時には判断コアを利用可能な実行単位にし、その後で対局進行と各アダプタを組み合わせます。

アダプタが判断コアを参照でき、設定と固定パラメータが同じ実行基準位置から解決できることが実行の前提です。依存ライブラリ、並列実行機能、OS とバイナリ互換性が一致しない場合は、判断前に起動へ失敗します。

OS 別の生成手順、成果物の名前、依存ライブラリの確認は [akochan/readme_jpn.md](../akochan/readme_jpn.md)（日本語）または [akochan/readme.md](../akochan/readme.md)（英語）を参照してください。英語版には自己対局の補足があります。ここではビルド操作ではなく、判断コアと実行アダプタの配置関係だけを扱います。

### 2.2 実行前の確認

自己対局やログ解析では、設定ファイルと `params/` が同じ実行基準位置から見えることを確認します。設定には対局設定と AI の戦術設定があり、固定重みの学習手順はこのリポジトリには含まれません。

## 3. CLI の利用形態

### 3.1 自己対局

自己対局は `system.exe test 1000 1001` のように、対局の種別と乱数 seed の範囲を指定して実行します。範囲を省略した場合の既定値や起家の扱いは設定に従います。各 seed と起家の組合せごとに記録を作り、結果ディレクトリへ設定のコピーと牌譜ログを保存します。

付属設定の `chicha` は起家の一覧です。`test` の既定 seed 範囲は1000以上1001未満で、指定した範囲と `chicha` の各要素の組合せごとに `haifu_log_<seed>_<chicha>.json` を出力します。設定の `result_dir` には、実行時に使った設定のコピーも保存されます。

1局の流れは、局開始、起家のツモ、判断と行動、他家の応答、和了または流局、局終了、次局開始です。自己対局では4人とも同じ判断機構から行動を選びます。進行中のイベントが診断情報とともに標準出力へ出るため、自己対局の標準出力をそのまま MJAI 応答ストリームとして扱うことはできません。

`initial_condition_match` は既存ログから指定局の点数と局番号を初期条件として再開します。対応する初期ログと設定キーが必要で、通常の `test` と乱数の初期化経路が異なるため、同じ seed だけで完全に同じ山になるとは限りません。

このモードを使うには、設定に `initial_dir` と `kyoku_init` を用意し、`initial_dir/haifu_log_<seed>_0.json` のような初期ログを置きます。付属の設定には初期条件がないため、そのままでは再開モードを実行できません。

### 3.2 ログの確認とレビュー

| 形式 | 目的 |
|---|---|
| `system.exe check` | 牌譜を順に再生し、イベントの進行を確認 |
| `system.exe mjai_log <file> <id>` | 指定局面の全候補とレビュー情報を表示 |
| `system.exe mjai_log <file> <id> <line_index>` | 指定行までを再生してレビュー |
| `system.exe full_analyze <file> <id>` | AIの最良候補と実際の選択の差を各判断点へ記録 |
| `system.exe legal_action <JSON文字列>` | その時点の合法な単一行動を列挙 |
| `system.exe legal_action_log_all <file>` | 牌譜の各行で合法な単一行動を列挙 |

`full_analyze` は、次のイベントが存在する判断点、通常の打牌や応答を主な比較対象とします。短いログ、槓や嶺上和了を含む特殊な列、次イベントが欠けた末尾はレビューの前提から外れます。

### 3.3 統計

`system.exe stats <dir_name>` は複数の自己対局ログから順位、平均順位、リーチ、鳴き、和了、放銃を集計します。`system.exe stats_mjai [dir_name [player_name_prefix]]` は MJAI ログから名前の接頭辞に一致するプレイヤーを選んで集計します。空ディレクトリや不完全ログでは、集計に必要な分母が得られずエラーになる場合があります。

`stats` は `setup_match.json` を集計対象から除き、プレイヤーごとの回数と局あたり率を出します。`stats_mjai` は `.mjson` を対象に、名前の接頭辞で最初の該当プレイヤーを選びます。対象が複数または存在しない場合は、意図したプレイヤーを明示できる名前付けが必要です。

## 4. 自己対局の進行

### 4.1 山と配牌

1局の開始時に136枚の物理牌を作り、乱択してから赤5を含む牌種表現へ変換します。最初の52枚を4人へ13枚ずつ配り、起家を基準に座順を決めます。通常ツモは配牌の後ろから進み、嶺上ツモは山の末尾側から取ります。通常ツモと嶺上ツモを合わせた上限は70回です。初期の表ドラは山の末尾から6枚目を使います。

自己対局の局開始イベントには配牌、点数、表ドラ、山全体などが含まれます。他家の牌を `?` に隠す補助機能はありますが、自己対局や TCP 接続で自動的に適用される機能ではありません。

### 4.2 イベントを進める優先順位

打牌または加槓の後は、次の優先順位で処理します。

1. 他家のロンを調べる。
2. ツモ総数が上限なら流局にする。
3. 加槓の直後なら嶺上ツモに進む。
4. ポンを調べる。
5. 大明槓を調べる。
6. 下家のチーを調べる。
7. リーチ受理や必要なカンドラを追加し、次のツモへ進む。

複数人がロンできると、複数の和了イベントが同じ進行で追加されることがあります。鳴きはポン、大明槓、下家のチーの順で、同じ種類の候補が複数ある場合は座順に依存します。

### 4.3 次局

和了または流局の後は、親の連荘、本場、局番号、場風を更新して次の局を開始します。親の和了、または流局時の親のテンパイで連荘し、九種九牌は同じ局をやり直します。点数が0未満になった場合や規定の最終局条件では半荘を終えます。自己対局経路の半荘種別は現行設定で東風戦に固定されています。

## 5. 二段階行動と MJAI

### 5.1 行動の単位

判断結果は、単一イベントまたは二つの連続イベントです。

| 判断場面 | 返すイベント | 受け手の処理 |
|---|---|---|
| 自分のツモで打牌 | `dahai` | 1件を受理 |
| 自分のツモで和了 | `hora` | 1件を受理 |
| 自分のツモで槓 | `ankan` または `kakan` | 1件を受理 |
| 自分のツモでリーチ | `reach` → `dahai` | 1件目の受理後に2件目 |
| 他家の打牌でロン | `hora` | 1件を受理 |
| 他家の打牌でポン・チー | `pon`/`chi` → `dahai` | 宣言の受理後に打牌 |
| 応答しない | `none` | 応答を省略 |

リーチ、ポン、チーの2件目は、1件目が受理されてから送ります。接続側は未送信の2件目を保持し、対応する受理イベントを受けた時点で送る必要があります。

### 5.2 TCP 接続

TCP 版は既定で `127.0.0.1:11600` に接続し、改行区切りの1行 JSON を送受信します。外部サーバーから `hello` を受けると `join` を返し、`start_game` で自分の ID を保存します。自分の `tsumo`、または他家の `dahai` で応答可能な場合に判断し、それ以外のイベントには `none` を返します。

`setup_mjai.json` は接続設定と1人分の戦術設定を持ちます。起動スクリプトの外部サーバー、ポート、対局種別、ログ先が一致していることを確認します。共有ライブラリの探索パスが必要な OS では、成果物のあるディレクトリを探索対象に加えます。

### 5.3 TCP で受け取るイベント

| 受信イベント | 反応 |
|---|---|
| `hello` | 参加要求を返す |
| `start_game`、`start_kyoku` | 記録へ保存し、通常は `none` を返す |
| 自分の `tsumo` | 判断して最良候補を返す |
| 他家の `dahai` と応答可能な情報 | 判断して最良候補を返す |
| 自分の `reach`、`pon`、`chi` | 保持していた二段階行動の2件目を返す |
| `hora`、`ryukyoku`、その他 | 記録し、`none` を返す |

通信の受信側は、開始局の点数を保存し、次の局開始で点数が省略された場合に保存値を補います。入力イベントの構文エラーやソケット障害では回復せず終了する経路があります。

## 6. 標準入出力と一手 API

### 6.1 `pipe` / `pipe_detailed`

`system.exe pipe <tactics.json> <id>` はイベントを標準入力から1行ずつ受け、指定プレイヤーの判断時だけ結果を標準出力へ返します。`pipe_detailed` は候補とレビュー情報を返します。入力側が返答を記録へ反映し、次のイベントを送る責務を持ちます。

両者とも局開始で新しい局を始め、`error` などの管理イベントを無視します。自分のツモ、他家の打牌・加槓が判断点ですが、TCP 版と異なり、標準入力版は他家の打牌に応答可能かどうかを入力側が保証する前提があります。

`pipe` はイベントに `can_act=false` があれば処理を止めますが、`pipe_detailed` はこのフラグを見ずにイベント種別を判断します。また、標準入力版は返した行動を内部の記録へ戻さないため、継続利用する側が応答を次の入力へ反映します。

### 6.2 `game_server`

`system.exe game_server '<JSON文字列>'` は TCP サーバーではなく、1回の入力で対局状態を1ステップ進める API です。入力は記録 `record`、外部からの要求 `request`、起家 `chicha`、必要なら山 `haiyama` を持ち、出力は差分イベント `new_moves`、状態種別 `msg_type`、必要なら合法手 `legal_moves` を持ちます。

この API ではプレイヤー0が外部入力の対象で、他の3人は自動選択です。宣言（リーチ、ポン、チー）の直後は、次の呼び出しで同じプレイヤーの打牌を渡します。新しい判断を要求する状態では `update_and_dahai` または `update_and_fuuro`、不合法な要求を再送させる状態では `dahai_again` または `fuuro_again` が返ります。

入力記録が空なら、最初の呼び出しは開始イベントだけを追加します。初局では起家が必要で、山を省略した場合は記録内の局開始から山を探します。外部の MJAI ログのように山を省略した記録では、初局を再構成できない場合があります。返される `new_moves` は入力記録との差分であり、自動選択された他家のイベントも含みます。

## 7. 設定と固定パラメータ

自己対局設定は4人分の戦術設定を持ち、MJAI・レビュー・標準入出力・一手 API は1人分の設定を4人へ複製します。設定には候補数、DP、槓、降り、順位点、確率モデルの選択などが含まれます。

設定の読み込みには二つの境界があります。共通の戦術設定として構造化される項目と、各確率計算が設定 JSON を直接参照する項目です。新しいキーを加えた場合、どちらの経路が読むかを確認しないと設定は効きません。固定パラメータの不足や設定の型・要素数の不整合は、代替値へ補完せず停止する場合があります。

付属設定の順位点は `[90,30,-30,-90]`、基底設定は `default` です。MJAI・レビュー・標準入力・一手 API では、1つの戦術オブジェクトを4人へ複製します。自己対局では4人分の配列要素をそれぞれのプレイヤーへ割り当てます。

## 8. 実装上の境界

以下は運用上重要ですが、一般的な MJAI や麻雀の原理ではなく、現行実装の挙動です。

- TCP 版は診断文字列を標準出力へ出すため、JSON だけを要求するサーバーとの互換性が保証されません。
- TCP の引数の一つがポートと受信ログ名の両方に使われる経路があり、標準起動例でも意図しないログファイルが作られることがあります。
- 他家の加槓を受信したとき、AI 本体や標準入力版には槍槓候補がある一方、TCP 版はそのイベントで AI を呼ばず `none` を返す経路があります。
- `request.type == "pass"` は一手 API の合法性検査を迂回します。自分のツモ後など、進行しない局面へ送らないでください。
- 自己対局の嶺上牌の取り方、海底付近の槓、複数ロンの点数処理、和了直後の点数状態は標準ルールと一致しない場合があります。
- ログのレビュー・統計は完全な JSON Schema 検証や不完全入力の回復を目的としていません。
